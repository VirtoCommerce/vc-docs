# Virto Commerce Rosetta

> Cross-vendor concept mapping sub-index of the Virto Commerce AI documentation hub. Translates Virto Commerce vocabulary to Shopify, Adobe Commerce (Magento), commercetools, and BigCommerce. Use this when an AI agent needs to answer "I know how X works in vendor Y, how do I do X in Virto?". Mappings are approximate; near-matches are noted, and important nuances are called out under "When the analogy breaks". For Platform/backend, Frontend, Marketplace, VC-Shell, or Cloud, see the parent hub at https://docs.virtocommerce.org/llms.txt.

⚠ This file uses *approximate* mappings to enable cross-vendor reasoning. A "≈" in a table means "closest analog", not "exact equivalent". Always verify implementation specifics in the linked Virto docs before generating code or schema.

## How to use this file

When a developer asks "how do I do X in Virto, given I know it as Y in vendor Z":
1. Look up Y in the table for vendor Z.
2. Read the Virto column for the closest concept.
3. Follow the linked doc page in the [Platform sub-index](https://docs.virtocommerce.org/llms/platform.txt) for implementation details.
4. Check "When the analogy breaks" for known gotchas.

## When the analogy breaks

Use this section when a one-line mapping isn't enough.

- **Virto is open-source and self-hostable; Shopify, commercetools, and BigCommerce are SaaS-only.** This affects deployment, customization depth, and how "extensions" are conceived. Shopify Apps run *outside* Shopify; Virto modules run *inside* the platform.
- **Virto's Module is a vertical slice (Module.Core / Module.Data / Module.Web).** Magento's Module concept is similar, but Shopify Apps and commercetools API Extensions are external services, not in-process code. Pattern translation matters.
- **Virto Dynamic Properties ≈ Shopify Metafields**, but Dynamic Properties are typed and queryable through standard query infrastructure; Shopify Metafields require explicit definition and have query restrictions.
- **B2B is first-class in Virto** (Quotes, Organizations, Contracts, contract pricing) without an enterprise tier. In Shopify it requires Shopify Plus + B2B Catalogs; in Adobe Commerce it requires the B2B feature set; in commercetools it uses Business Units (newer feature).
- **Headless is the default in Virto.** All admin and backend logic is exposed via REST and GraphQL xAPI; vc-frontend is one possible Frontend, not "the" Frontend. Shopify and BigCommerce default to bundled themes and only optionally go headless.
- **Marketplace is a first-party Virto product**, with Operator Portal, Vendor Portal, and State Machine module shipped together. Competitor mappings in the Marketplace table are typically third-party (e.g., Mirakl) or DIY.
- **No EAV.** Virto uses typed entities + Dynamic Properties; if you're translating from Magento's EAV model, expect simpler queries, less flexibility for arbitrary types, and predictable schema.
- **No Liquid template language.** Virto's Frontend is Vue 3 components. Translating Shopify Liquid sections requires rewriting in Vue, not just file-format conversion.

## Vocabulary cheat sheet

- "Frontend" in Virto = customer-facing storefront. Use **Frontend**, not "storefront" (per the [vc-docs style guide](https://raw.githubusercontent.com/VirtoCommerce/vc-docs/main/CLAUDE.md)).
- "Backoffice UI" = legacy AngularJS admin SPA (today's main admin). Sometimes called "admin SPA" or "Platform Manager".
- "xAPI" = the GraphQL Frontend-optimized API gateway. Always written **xAPI**, never "XAPI".
- "PBC" = Packaged Business Capability — a curated bundle of modules with a `package.json` manifest.
- "Module" = vertical-slice .NET module (Module.Core + Module.Data + Module.Web). Not equivalent to "Shopify App" or "commercetools API Extension".
- "Atomic Architecture" = Virto's MACH-aligned compositional model (Atoms → Molecules → Cells → Organisms).

→ More terms: [Glossary](https://docs.virtocommerce.org/platform/developer-guide/latest/glossary/) · [vc-docs style guide](https://raw.githubusercontent.com/VirtoCommerce/vc-docs/main/CLAUDE.md).
