## 1. concepts/architecture.md

### Верифицировано

- Слои `framework/core`, `framework/ui`, `framework/shell` существуют, содержат описанные сущности.
- `useApiClient(ClientCtor)` — точка входа к Platform (с оговорками, см. ниже).

- Filter remote entries by dependency ranges — подтверждено: semver-проверка `compatibleWith.dependencies["@vc-shell/framework"]` против текущей версии (line 179-190).
- Default Vue plugin export — подтверждено через `resolvePlugins` (line 81-98), обрабатывает `default.install`, `module.install` и рекурсивный вариант.

### Расхождения

- **Wrong:** "host reads `/api/frontend-modules`" — подразумевает GET. Фактически **POST** с body `{ appName, provides }` (mf-host line 156-161). Не критично, но имплицирует REST-семантику, которой нет.
- **Wrong/Incomplete:** "Shared dependencies keep Vue, Vue Router, vue-i18n, and `@vc-shell/framework` as singletons" — реальный список шире: `vue, vue-router, vue-i18n, vee-validate, lodash-es, @vueuse/core, @vc-shell/framework` плюс subpath-экспорты `@vc-shell/framework/ui`, `@vc-shell/framework/ai-agent`, `@vc-shell/framework/extensions` (mf-host RUNTIME_LIBS, line 30-45). Subpath-экспорты — содержательная деталь: без них remote ловит дубликат фреймворка.
- **Imprecise:** "Application code connects to Platform through generated TypeScript clients and `useApiClient(ClientCtor)`" — `useApiClient` сейчас почти пустая обёртка (см. секцию 6). Утверждение про "back-office user experience" и тоновая часть корректны.

### Missing / Outdated

- Нет упоминания контракта `IAuthApiBase` — это публичная граница между фреймворком и генерированными клиентами, важная для понимания "как клиенты подключаются".
- Нет упоминания, что fetch-интерсептор (`registerInterceptors`) перехватывает только запросы к `/api/*` на том же origin (interceptors/index.ts:56-65) — это инвариант, который определяет, что попадает под Platform-контракт.

### Вердикт: **PATCH**

Конкретные правки:
1. В разделе "Remote Extensions" заменить "host reads `/api/frontend-modules`" на "host POSTs to `/api/frontend-modules` with `{ appName, provides }` and receives a registry of compatible remote entries".
2. Расширить список singletons: добавить `vee-validate`, `lodash-es`, `@vueuse/core` и framework subpath-экспорты.
3. Опционально: в разделе "Platform Boundary" добавить одно предложение про `IAuthApiBase` как контракт для генерируемых клиентов.

## 5. concepts/extensions.md

### Верифицировано

- `defineExtensionPoint("id", options?)` returns `{ components: ComputedRef sorted by priority asc, hasComponents: ComputedRef<boolean> }` — точно (defineExtensionPoint.ts:41-55).
- `useExtensionPoint(name)` returns `{ add, remove }` — нет отдельного `replace` (useExtensionPoint.ts:20-42).
- `add` идемпотентен по id: replace at index или push (useExtensionPoint.ts:24-31).
- Priority ascending, lower first, default `0` (defineExtensionPoint.ts:49: `(a.priority || 0) - (b.priority || 0)`).
- Equal priority preserves registration order — следствие стабильной сортировки в JS (Array.prototype.sort stable since ES2019). Корректно.
- Console warning точно: `[vc-shell] Extension point "${name}" is not declared. Available: ${declared.join(", ") || "(none)"}` (store.ts:40-42). Доковая цитата сокращённая, но не противоречит.
- Order independent: consumer может зарегистрировать до host'а — `getPoint` создаёт `undeclared` entry, потом `declarePoint` его "обновляет" (store.ts:19-26).
- ExtensionPoint component prop `name` обязательный, плюс `separator`, `gap`, `wrapperClass` — подтверждены (ExtensionPoint.vue:43-56).

### Расхождения

- **Wrong/Imprecise:** "Extension points live in an **app-scoped** reactive registry". Это **не app-scoped** — это **module-singleton** `reactive<Record<string, ExtensionPointState>>({})` на верхнем уровне `store.ts:4`. При Module Federation с shared singleton `@vc-shell/framework` это эффективно одна общая registry на все host/remotes, что и есть желаемое поведение. Но в multi-tenant scenario или при двух разных install'ах фреймворка в одном процессе они не были бы изолированы по app. Терминология "app-scoped" вводит в заблуждение.
- **Missing:** `<ExtensionPoint>` имеет prop `filter: Record<string, unknown>` который **реально использует** `meta` для фильтрации (ExtensionPoint.vue:54-71). Доc упоминает "optional `meta` for filtering" в entry shape, но не показывает, **как** фильтровать. Это исполнимый прецедент использования meta.
- **Missing:** `<ExtensionPoint>` поддерживает **scoped slot** (ExtensionPoint.vue:2-7) для полного контроля рендера хостом. Не упомянуто в концепте.
- **Missing:** prop `separatorClass` (доп. кастомизация разделителя), `wrapperClass` (доc упоминает), `gap` (упоминает). Минор.

### Missing / Outdated

- Не показан typed-meta дженерик: `defineExtensionPoint<MyMeta>(...)` (defineExtensionPoint.ts:41 docstring). Это полезный паттерн для type-safe meta — стоит упоминания.
- Не показан паттерн `add({ ..., meta: { type: "action" } })` плюс `<ExtensionPoint filter="{ type: 'action' }" />` — реальный use case для meta.

Конкретные правки:
1. Заменить "app-scoped reactive registry" → "framework-singleton reactive registry" или "shared reactive registry living inside `@vc-shell/framework` (singleton under Module Federation)".

## 6. concepts/api-clients.md

### Верифицировано

- Generated клиенты эмитируются под `src/api_client/<platform-module>/` (по конвенции; см. cli/api-client — не проверил подробно, но название `@vc-shell/api-client-generator` — реальный пакет).
- `useApiClient(ClientCtor)` returns `{ getApiClient }` async factory — точно (useApiClient/index.ts:14-25).
- `useAsync` пара с `{ action, loading }` — общая конвенция, ОК.
- Generated client constructor: `new (baseUrl?: string, http?: { fetch }) => ApiClient` (useApiClient/index.ts:15) — соответствует.

### Расхождения

- **CRITICAL Wrong:** Доc утверждает: *"The base URL is filled in from `APP_PLATFORM_URL`, the OAuth token is attached, and token rotation is handled automatically."*. **Это неточно для `useApiClient` как такового.** Тело функции — буквально:
  ```ts
  async function getApiClient() {
    const client = new c();
    return client;
  }
  ```
  Никакого env var, токена, ротации. Реальность:
  - **Base URL**: должен резолвиться через `IAuthApiBase.getBaseUrl(defaultUrl, baseUrl)` внутри генерируемого клиента или через `defaultBaseUrl`, передаваемый при конструировании (в коде useApiClient не передаётся — `new c()` без аргументов). То есть либо генератор зашивает default из APP_PLATFORM_URL в конструктор, либо клиент использует относительные пути (`/api/...`) и попадает под fetch-интерсептор на том же origin.
  - **Auth токен**: контракт `IAuthApiBase` имеет `setAuthToken(token: string)`, но **`useApiClient` его не вызывает**. Токен должен прицепляться либо генерируемым клиентом через cookie (browser-managed session), либо отдельным механизмом, либо через subclass/wrapper.
  - **Token rotation**: тот же 401-redirect живёт в fetch-интерсепторе (`registerInterceptors`, interceptors/index.ts:105-114) — но это **logout-on-401**, не ротация. Никакой ротации токена в коде нет.
- **Wrong/Misleading:** "for third-party or non-platform APIs that do not extend `AuthApiBase`" (фраза попадается в auto-gen useApiClient.md и в основном useApiClient.docs.md) — концепт-страница про `AuthApiBase` **молчит**. Это центральный контракт; без него цитата useApiClient выглядит магией.

### Missing / Outdated

- **Контракт `IAuthApiBase`** — `authToken: string`, `setAuthToken(token)`, `getBaseUrl(defaultUrl, baseUrl)`. Все генерируемые клиенты должны его реализовать. Доc не упоминает.
- **Token attachment механизм** — на самом деле не задокументирован ни в концепт-странице, ни в auto-gen reference чётко. Это реальный белый пятна, требующий уточнения с автором фреймворка.
- `useDataTablePagination` сигнатура — не проверял в этом батче, но shape `{ pageSize, totalCount, onPageChange }` правдоподобен. Стоит сверить отдельно.
- `useTableSort` vs `useDataTableSort` — два разных композабла, доc использует `useTableSort` для concept-пример (это canonical для строки sort).
- Команда `yarn generate-api-client` — не проверил в этом батче.

### Вердикт: **REWRITE** (раздел про "base URL / token / rotation")

Концептуальный фрейминг неверен: useApiClient — это **синхронизированный конструктор клиента**, а не auth-плагин. Auth и base URL приходят из **генерируемого клиента** (контракт `IAuthApiBase`), а 401-logout — из **fetch-интерсептора**. Эту трёхслойную картину надо прорисовать заново.

Обоснование REWRITE: текущий текст создаёт ложную модель ("useApiClient прицепляет токен"), которая ломается при отладке (разработчик не понимает, кто и где привязывает токен). Это не точечная правка формулировки; это переписать модель.

Альтернатива: **PATCH с уточнением** — добавить one-liner "Authentication and base URL are resolved by the generated client itself, which must implement `IAuthApiBase`" и удалить претензию, что useApiClient это делает. Но я бы взял **REWRITE** для intro-абзаца.

## 7. concepts/localization.md

### Верифицировано

- vue-i18n инстанцируется один раз с `legacy: false, globalInjection: true, locale: "en", fallbackLocale: "en", formatFallbackMessages: true` (i18n/index.ts:3-9).
- Modularity merges via `i18n.global.mergeLocaleMessage` — shallow per language code (modularity/index.ts:124).
- Storage key `VC_LANGUAGE_SETTINGS` — точно (`useLocalStorage("VC_LANGUAGE_SETTINGS", "")`, language-service.ts:23).
- `setLocale`: нормализует camelCase→kebab-case lowercase, валидирует против `i18n.global.availableLocales`, fallback `"en"`, обновляет `i18n.global.locale.value`, реконфигурирует vee-validate через `setVeeI18nLocale` + `localize`, пишет в `savedLocale.value` (language-service.ts:25-64). Всё совпадает.
- `currentLocale: ComputedRef<string>` (language-service.ts:39).
- `getLocaleByTag`, `getFlag`, `getCountryCode` — дополнительные методы service, не упомянуты концепт-доком (норма для concept-уровня).

### Расхождения

- **Misleading:** "On boot the service reads `VC_LANGUAGE_SETTINGS` first, then falls back to `APP_I18N_LOCALE` from `.env`". В `language-service.ts` **нет ссылки на APP_I18N_LOCALE**. ## 8. concepts/permissions-model.md

### Верифицировано

### Расхождения

- **CRITICAL Wrong:** Доc утверждает: *"`hasAccess(undefined)` and `hasAccess([])` return `true`. No restriction means visible."*. Это **неверно для пустого массива**. Разбор кода:
  ```ts
  if (!permissions || user.value?.isAdministrator) { return true; }
  else if (Array.isArray(permissions)) { return permissions.some(...) }
  ```
  Для `permissions = []`:
  - `![]` = `false` (массив — truthy)
  - admin-проверка `false` (non-admin)
  - `Array.isArray([])` = `true`
  - `[].some(...)` = `false`
  
  Итог: **`hasAccess([])` returns `false`** для non-admin. Для admin — `true` (через short-circuit на ветке выше).
  
  Это противоречие между документированной семантикой ("no restriction means visible") и фактической семантикой ("empty array means restricted to none — visible only to admin"). Один из двух — баг: либо доc неправ, либо код неправ.

  Рекомендация: проверить намерение с автором кода. Если ожидание — что `[]` = "не ограничивает", надо добавить вторую короткую ветку (`Array.isArray(permissions) && permissions.length === 0`) → `return true`. Если ожидание — fail-closed, доку поправить.

- `hasAccess` выбрасывает Error при типе, отличном от string/array/undefined (line 23). Не отражено в доке.
- `useUser` (отдельный композабл) — также источник user object. Доc не путает, но контекст полный требует упоминания useUser vs useUserManagement.
